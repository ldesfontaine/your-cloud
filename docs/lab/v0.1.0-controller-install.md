# `v0.1.0` — installation d'un Controller depuis le lot embarqué

## Statut

Preuve de l'issue #38, exécutée le 5 août 2026 depuis **l'arbre de travail**, sur
la topologie `quick` du LAB Linux (`lab-console` et `lab-machine-1`). Elle porte
sur des sources non publiées : elle ne ferme aucune ligne de palier à elle
seule et ne vaut pas pour un candidat signé.

`lab-windows` est restée **éteinte** pendant toute la passe. Le module
`installation` compile sous `cfg(any(linux, windows))` mais rien de ce rapport
n'observe Windows.

Ce qui est prouvé : le lot est jugé avant tout privilège, le paquet installé est
exactement celui que le manifeste signé décrit, le Controller tourne isolé sous
son compte dynamique et ses budgets, il survit à l'arrêt réel de l'Assistant, de
la Console et de la machine qui les porte, et un échec à chacune des quatre
premières étapes laisse une machine que le déroulé du rollback reconstruit
exactement.

Ce qui n'est **pas** prouvé : voir « Ce que ce passage ne prouve pas ».

## Ce que le manifeste lie

Le manifeste est un objet JSON compact, sans retour à la ligne final, et la
signature Ed25519 détachée couvre **ses octets exacts**. Il n'y a aucune étape
de canonicalisation : ce qui est signé est ce qui est sur le disque.

| Champ | Valeur de cette passe |
|---|---|
| `schema_version` | `1` |
| `kind` | `your-cloud-server-bundle` |
| `version` | `0.0.3` |
| `target` | `debian-13-amd64` |
| `size` | `5542372` |
| `sha256` | `b7a691acba2735d5fbc28e46e06ede87fc2bf30f717a744e32aa091e6d45031e` |

L'ordre des contrôles fait partie du contrat et les tests l'imposent : bornes,
puis signature, puis sens, puis empreinte de l'artefact. Aucun octet non
authentifié n'atteint le parseur JSON.

### Incident de swap, et ce qu'il a appris au harnais

Le premier passage complet a fait rougir la suite `personal-access-contract`
sur un cas sans rapport avec #38 :

```text
---- a_crash_during_the_derivation_destroys_the_thread_the_file_and_leaves_no_secret stdout ----
panicked at crates/native-bootstrap-assistant/tests/personal_access_contract.rs:3436:5:
this machine has no swap to search at all
```

Cause : le swap de `lab-console` est un `/swapfile` activé à la main, absent de
`/etc/fstab`. L'étape `shutdown` de cette preuve arrête réellement la VM, et le
redémarrage l'a donc rendue sans swap. Le cas qui a rougi cherche la phrase
secrète dans le swap : sans swap, il n'a plus rien à fouiller et refuse de se
déclarer vert — ce qui est le comportement correct.

C'est un échec d'infrastructure causé par le harnais, pas un défaut du produit.
Correction retenue : `shutdown` relève désormais les zones de swap actives
**avant** d'arrêter la machine et les réactive après le redémarrage, en
échouant visiblement si elles ne reviennent pas. Un harnais qui arrête une
machine lui doit l'état qu'il a trouvé ; sans cela il dégrade silencieusement
le LAB pour toutes les suites suivantes.

## Ce que le paquet possède

Relevé sur la machine après installation, par `dpkg -L` et `stat` :

```text
/usr/lib/systemd/system/your-cloud-controller.service   root:root 644
/usr/lib/systemd/system/your-cloud-daemon.service       root:root 644
/usr/lib/systemd/system/your-cloud-relay.service        root:root 644
/usr/lib/your-cloud/your-cloud                          root:root 755
```

Aucun autre fichier n'est inventorié. `find -perm /6000` ne rend rien et
`getcap -r` ne rend rien : ni setuid, ni setgid, ni capacité de fichier. Le
paquet ne déclare que `Depends: systemd` ; le binaire Go est construit
`CGO_ENABLED=0 -trimpath`, donc sa fermeture de dépendances est satisfaite hors
ligne par le socle Debian 13.

Les trois unités sont livrées **inactives**. Après installation :

```text
your-cloud-controller.service   enabled     (activée par l'Assistant, une seule)
your-cloud-daemon.service       disabled
your-cloud-relay.service        disabled
```

Les scripts mainteneur se limitent à `systemctl daemon-reload`. Ils ne
téléchargent rien, ne génèrent aucun secret, n'activent aucun rôle et ne
suppriment aucun état persistant.

## Isolation du Controller en fonctionnement

Relevé par `systemctl show` et `ps` sur le service réellement démarré :

| Observation | Résultat |
|---|---|
| compte | `User=your-cloud-controller`, `DynamicUser=yes` — uid transitoire `65416`, aucun compte persistant |
| budgets | `TasksMax=128`, `MemoryMax=402653184` (384 Mio) |
| privilèges | `CapabilityBoundingSet=` vide, `NoNewPrivileges=yes` |
| système de fichiers | `ProtectSystem=strict`, état privé `0700` sous `/var/lib/private/your-cloud-controller` |
| secrets | les trois sources sont `root:root 0600` sous `/etc/your-cloud/controller-credentials` ; systemd seul les remet au service |
| écoute | `192.168.240.115:9443`, exactement l'adresse privée déclarée |

Les clés opérationnelles ne transitent ni par la ligne de commande, ni par
l'environnement, ni par la Console. Le service et `root` peuvent nécessairement
les lire à l'exécution : cette protection réduit l'exposition aux autres
comptes, elle ne protège pas d'une compromission complète de la machine.

## Refus exercés, chacun avec son contrôle positif

Tous ces verdicts sortent du module `installation` compilé, à travers le binaire
de fixture. Aucun d'eux n'est calculé par le harnais.

| Cas | Refus observé |
|---|---|
| le lot embarqué, inaltéré | `VERIFIED version=0.0.3 target=debian-13-amd64 size=5542372 sha256=b7a6…` |
| un artefact altéré d'un octet, même longueur | `DigestMismatch` |
| un artefact plus court d'un octet | `SizeMismatch` |
| un manifeste réécrit après signature | `SignatureNotByAnchor` |
| un manifeste signé par une clé qui n'est pas l'ancre | `SignatureNotByAnchor` |
| un lot que l'ancre a signé pour `arm64` | `UnsupportedTarget` |
| un lot que l'ancre a signé pour une autre version | `UnexpectedVersion` |
| un manifeste que l'ancre a signé pour un autre genre | `ForeignKind` |
| chaque endpoint déclaré répond sa clé confirmée | `CLEARED lab-console` |
| un endpoint présentant une autre clé d'hôte | `HostKeyMismatch` |
| un endpoint que le Controller ne joint pas | `Unreachable` |
| un endpoint dont la clé n'a jamais été confirmée | `NeverConfirmed` |
| un endpoint sur deux échoue | refus nommant `second-endpoint`, **aucune** habilitation partielle |
| un échec entièrement observé | `COMPLETE` dans l'ordre inverse de création |
| un paquet déjà présent | jamais retiré |
| un paquet à demi configuré | `INCOMPLETE`, retrait aveugle interdit |
| après transfert d'autorité | `AFTER_TRANSFER`, rien n'est défait |

Le placement public n'apparaît pas dans cette table parce qu'il ne peut pas y
arriver : `placement::propose` de #36 refuse un endpoint `Exposed` ou
`Intermittent` avec `ControllerOnExposedEndpoint` et
`ControllerOnIntermittentEndpoint`, donc aucune `Proposal` n'existe, donc
aucune `ApprovedPlacement`, donc `plan::authorize` n'a rien à recevoir. La
chaîne entière est parcourue par le test
`an_exposed_endpoint_never_reaches_this_module_at_all`.

## Prévol réellement joué depuis le Controller

La table ci-dessus juge des observations écrites. Cette étape-ci fait collecter
l'observation par la machine qui porte le Controller, puis la donne à la même
porte.

| Observation | Résultat |
|---|---|
| `ssh-keyscan` depuis `lab-machine-1` vers `lab-console` | `SHA256:a5cmnRL9bq5QAKqqeyr0hIk42h7KMXDsSZgeGmwy+uo` |
| confrontation à la clé confirmée par le canal géré | identiques |
| porte sur l'observation réelle | `CLEARED lab-console` |
| `ssh-keyscan` vers `192.0.2.1` (plage de documentation RFC 5737) | aucune réponse, comme attendu |
| porte sur cet endpoint | `REFUSED Unreachable { name: "unreachable-endpoint" }` |

C'est ce qui sépare « l'endpoint est joignable » de « l'endpoint est joignable
**depuis le Controller** » : la collecte est faite par `lab-machine-1`, pas par
le poste de pilotage ni par la Console.

## Arrêt réel de l'Assistant et de la Console

| Observation | Résultat |
|---|---|
| Controller avant | `pid=10718 state=active` |
| processus Assistant dans `lab-console` | tués, puis `pgrep` vérifie qu'aucun ne survit |
| `lab-console` | `labctl stop` — arrêt propre confirmé, état `shut off` dans l'inventaire |
| Controller après | `pid=10718 state=active` |
| écoute | le Controller écoute toujours sur `9443` |

Le PID est identique avant et après. C'est ce qui distingue « le Controller a
survécu » de « systemd l'a relancé » : une unité morte puis redémarrée aurait
elle aussi rendu `active`. La vérification est faite depuis le poste de
pilotage par le canal `labctl`, pas par quelque chose que la Console tenait
ouvert — la Console est éteinte au moment où la question est posée.

`lab-console` est ensuite redémarrée et repasse la garde d'inventaire.

## Rollback, mesuré à chaque étape

Le harnais arrête l'installation à quatre points nommés, récupère le registre
que l'étape a **réellement** produit, le fait juger par le déroulé de
l'Assistant, puis vérifie que la machine revient à son état initial.

| Arrêt | Ce que le registre contient | Déroulé |
|---|---|---|
| `package` | 1 entrée | `COMPLETE your-cloud-server` |
| `configuration` | 2 entrées | `COMPLETE /etc/your-cloud/controller.env,your-cloud-server` |
| `state` | 4 entrées | `COMPLETE …/authority.json,…/your-cloud-controller,…/controller.env,your-cloud-server` |
| `credentials` | 8 entrées | `COMPLETE` des 8, dans l'ordre inverse exact |

Après chaque arrêt, `remove` rend la machine à son état initial et **prouve**
l'absence de chaque élément ; un échec de cette preuve fait rougir la passe.
Aucun succès partiel n'est présenté comme un succès : un registre portant une
seule provenance `UNKNOWN` rend `INCOMPLETE`, et le harnais traite `INCOMPLETE`
comme un refus.

## Épreuve par mutation

Trois mutations ont été introduites dans l'arbre, exécutées, puis retirées.
Chacune porte sur une propriété centrale de l'issue.

**Mutation A — le lot n'est plus confronté à son empreinte.** La branche
`DigestMismatch` de `bundle::verify` est rendue inatteignable.

```text
test installation::bundle::tests::an_artefact_that_is_not_the_one_the_manifest_binds_is_refused ... FAILED
assertion `left == right` failed
  left: Ok(VerifiedBundle { version: "0.0.3", target: "debian-13-amd64", size: 40, sha256: "8637edc5…" })
 right: Err(DigestMismatch)
test result: FAILED. 37 passed; 1 failed
```

**Mutation B — un prévol échoué habilite quand même les endpoints qui ont
répondu.** `preflight::clear` n'accumule plus que les tentatives acceptées au
lieu de refuser l'ensemble.

```text
test installation::preflight::tests::one_endpoint_failing_denies_the_clearance_of_every_other ... FAILED
test installation::preflight::tests::a_key_that_is_not_the_confirmed_one_is_refused_however_well_formed ... FAILED
assertion `left == right` failed
  left: Ok(PreflightCleared { endpoints: [] })
 right: Err(HostKeyMismatch { name: "machine-1" })
test result: FAILED. 34 passed; 4 failed
```

**Mutation C — un état inconnu est retiré aveuglément.** Le filtre du déroulé
passe de « créé par cette exécution » à « pas trouvé sur place ».

```text
test installation::rollback::tests::an_unknown_outcome_removes_nothing_of_itself_and_downgrades_the_unwind ... FAILED
assertion `left == right` failed
  left: ["/var/lib/your-cloud-controller", "your-cloud-controller.service", "your-cloud-server"]
 right: ["/var/lib/your-cloud-controller", "your-cloud-server"]
test result: FAILED. 36 passed; 2 failed
```

Les trois mutations ont été retirées et la suite est repassée verte
(`246 passed; 0 failed`).

## Ce que ce passage ne prouve pas

- **L'ancre n'est pas scellée.** La fonction de vérification **exige** une ancre
  et n'en fabrique aucune ; où cette ancre est scellée dans l'installateur de la
  Console reste hors périmètre de #38. Le harnais génère une ancre synthétique
  au montage et la détruit au démontage. La preuve porte donc sur « l'Assistant
  refuse ce que l'ancre n'a pas signé », pas sur « l'ancre est la bonne ».
- **Le lot n'est pas encore embarqué dans l'installateur de la Console.**
  `tauri.conf.json` n'emporte pas le `.deb` ; le lot est construit par la preuve
  et déposé dans `lab-console`. Le critère « aucun binaire privilégié téléchargé
  dynamiquement » est vérifié au sens où rien n'est téléchargé, pas au sens où
  l'empaquetage final est réalisé.
- **La collecte du prévol est faite par `ssh-keyscan`, pas par le Controller
  lui-même.** L'observation vient bien de la machine qui porte le Controller,
  mais c'est un outil du système qui ouvre le transport, pas le code du produit.
  Le module qui fera cette collecte depuis le Controller reste à écrire ; ce
  passage prouve la décision et l'origine de l'observation, pas son collecteur.
- **Le `.deb` n'est pas reproductible octet pour octet.** Deux constructions
  successives des mêmes sources donnent des tailles et des empreintes
  différentes, `dpkg-deb` inscrivant les horodatages des fichiers. Le manifeste
  lie donc l'artefact d'un passage donné, ce qui suffit au contrat de cette
  issue, mais une reproductibilité de la chaîne d'approvisionnement reste à
  obtenir et n'est pas revendiquée ici.
- **Aucune cible n'est mutée** — c'est le hors-périmètre déclaré de l'issue. Le
  Relay pointé par le Controller n'existe pas : le service démarre, écoute et
  survit, mais il ne dialogue avec aucun Relay réel.
- **L'association Console–Controller est décidée mais pas exercée.**
  `association::bind` est couvert par ses tests ; aucune association réelle
  n'est établie contre le Controller de cette passe.
- **Un seul endpoint déclaré.** La topologie `quick` porte deux VM ; l'endpoint
  déclaré est `lab-console` elle-même. Le cas « un endpoint sur deux échoue »
  est exercé sur des observations, pas sur deux machines réelles.
- Les identités SSH par cible, la commande forcée de l'Auxiliaire et le
  transfert d'autorité appartiennent aux paliers suivants.

## Nettoyage

`tests/lab/v0.1.0/controller-install/prove remove` rend les deux machines à leur
état initial et échoue visiblement s'il ne peut pas prouver l'absence de ce
qu'il a retiré. Sortie observée : `REMOVE_CONTROLLER_OK` puis
`perimeter removed from both machines`.

Les deux VM Linux restent démarrées ; ce harnais ne crée ni ne détruit de
topologie. `tools/labctl assert-clean` reste donc rouge par construction : la
fermeture LAB explicite est celle de [`docs/lab/README.md`](README.md).
