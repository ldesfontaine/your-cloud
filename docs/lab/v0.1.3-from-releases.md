# `v0.1.3` — le parcours d'un inconnu, depuis la page Releases

## Statut

Preuve exécutée le 20 août 2026 par
[`tests/lab/v0.1.3/from-releases/prove`](../../tests/lab/v0.1.3/from-releases/prove),
machines `lab-vps` (le poste) et `lab-machine-1` (le serveur), topologie
`quick`.

**Le parcours aboutit — mais pas depuis la page.** Un inconnu qui suit
littéralement ce que la page publie est arrêté dès la deuxième commande, et la
vérification qu'elle promet lui est inatteignable. Une fois l'installation
faite par la commande que la page ne donne pas, le trajet mène bien à « Le
Controller est actif sur la machine. » en **30 secondes** — mais seulement sur
une configuration de compte que **rien ne documente**, et que ni la
configuration par défaut de Debian ni le conseil du produit lui-même ne
produisent.

Six écarts sont mesurés ci-dessous. Deux appartiennent au README (`#150`),
deux au produit et **remontent au mainteneur**, deux sont mineurs.

**Les trois critères de `#149` sont tenus depuis la passe du soir.** La
première passe (après-midi) les a mesurés à leur état d'alors : le README ne
portait aucune section d'installation, et les deux commandes des notes de
release échouaient. `#150` a écrit cette section à partir de ce rapport, `#157`
a rendu les deux refus muets parlants, et le rejeu du soir est **vert** — les
quatre commandes que le README publie, jouées dans son ordre sur une machine
nue, mènent à `VERIFIED`, puis le parcours mène au Controller actif en
**31 secondes**.

## Ce que « le parcours d'un inconnu » veut dire ici

Rien ne vient du dépôt cloné. Le paquet est celui que la page publie, son
empreinte est celle que les notes annoncent, et chaque commande **produit**
jouée vient de la page. Ce que la page ne donne pas n'a pas été comblé depuis
le harnais : il est mesuré comme écart.

| | |
|---|---|
| Le poste | `lab-vps` — Debian 13.5 `amd64` nue, 1 vCPU / 967 Mio / 10 Gio, **322 paquets**, ni Go, ni Rust, ni Node, ni X. Instantané `vierge` pour rejouer |
| Le serveur | `lab-machine-1` — une machine que l'inconnu possède déjà, avec un compte administrateur et sa propre clé SSH |
| La source | la page Releases publique et le README publié — rien d'autre |

**Ce que le harnais apporte, et qui n'est pas le produit.** Un utilisateur réel
a un écran et des yeux ; cette machine n'en a pas. Le harnais installe donc un
serveur X virtuel (`xvfb`), de quoi publier un bus de session (`dbus-x11`), un
clavier synthétique (`xdotool`) et le pilote qui lit ce que la WebView peint
(`WebKitWebDriver`, plus `tauri-driver` **porté** depuis la machine de build
plutôt que compilé ici — installer Rust sur le poste d'un inconnu serait
exactement le provisioning que cette preuve refuse). Aucun de ces outils
n'installe le produit ni ne remplace un maillon du trajet.

**L'ordre des phases est une propriété, pas une commodité.** Les yeux du
harnais (`webkit2gtk-driver`) **dépendent de `libwebkit2gtk`** — la
bibliothèque dont l'absence est justement le premier écart. Monter le poste
avant de jouer la commande de la page ferait réparer par le harnais le défaut
qu'il doit mesurer. Mesuré : la première passe a rendu un vert qui mentait,
avant que l'ordre soit corrigé.

## Ce que la page offre, et ce qu'elle vaut

La page porte tout ce qu'il faut pour **identifier et vérifier** le fichier :
le nom (`your-cloud_0.1.3_amd64.deb`), l'empreinte
(`9fcb293e…`), et quatre artefacts. Lecture : **moins d'une seconde**.

### Le deuxième critère est tenu

```text
publiée : 9fcb293eca2e353c652736a141937563dd19942e60fdd5e7c01266f7709f3481
mesurée : 9fcb293eca2e353c652736a141937563dd19942e60fdd5e7c01266f7709f3481   CONCORDE
altéré  : 898815e3086647311ee4aa0136c49debf462b63c072e71f3871110453c82ed91   REFUSÉ
```

Téléchargement : 14 012 326 octets, moins d'une seconde. Un octet inversé au
milieu du fichier, et l'empreinte publiée cesse de le reconnaître — le contrôle
que la page met entre les mains de l'inconnu fonctionne.

### Écart n°1 — la commande d'installation de la page échoue (bloquant)

```text
$ sudo dpkg -i your-cloud_0.1.3_amd64.deb
 your-cloud depends on libwebkit2gtk-4.1-0; however: not installed
 your-cloud depends on libgtk-3-0; however: not installed
dpkg: error processing package your-cloud (--install): dependency problems
```

Code 1. Le paquet reste `iU` — déballé, non configuré. **La page n'offre
aucune suite.**

### Écart n°2 — la vérification promise est inatteignable (bloquant)

La troisième commande de la page, jouée dans son ordre juste après :

```text
$ /usr/bin/your-cloud-native-bootstrap-assistant --verify-embedded-server-bundle
error while loading shared libraries: libgtk-3.so.0: cannot open shared object file
```

Code 127. La page promet un `VERIFIED` que ses propres commandes rendent
impossible à obtenir.

### La continuation — ce qu'un README juste donnerait

Nommée comme telle, hors des critères, pour qu'une seule passe découvre tous
les écarts plutôt qu'un par rejeu :

```bash
sudo apt update
sudo apt install ./your-cloud_0.1.3_amd64.deb
```

Mesuré sur la machine nue : `apt update` **42 s**, `apt install` **186 s**
(≈ 200 Mio de dépendances). Le paquet passe `ii`, et la troisième commande de
la page rend enfin son verdict :

```text
VERIFIED version=0.1.3 target=debian-13-amd64 size=6082424 sha256=a9658b62…
```

## Les deux écarts qui appartiennent au produit

Ils remontent au mainteneur : ce ne sont pas des manques de documentation, mais
des refus qui ne nomment rien, sur les deux configurations de compte les plus
répandues au monde.

### Écart n°3 — le compte administrateur ordinaire d'une Debian est refusé, sans un mot

Le compte que l'installateur Debian produit quand on répond « oui » à « cet
utilisateur peut-il administrer la machine » : membre du groupe `sudo`, un mot
de passe. Le prévol du produit ne peut pas **lire** sa politique :

```text
$ LC_ALL=C /usr/bin/sudo -N -n -l -l
sudo: a password is required                      (code 1)
```

Le produit refuse alors, à raison, d'envoyer un mot de passe à une politique
qu'il n'a pas pu attester — c'est une propriété de sécurité, écrite et voulue.
Mais l'issue rendue à l'humain est :

> L'Assistant n'a pas pu conclure cette session. Rien n'a été approuvé, et rien
> de partiel n'est annoncé comme un succès.

Cette phrase ne nomme **ni la cause, ni le geste suivant**. La fenêtre de mot de
passe sudo n'apparaît jamais. C'est exactement le défaut que l'arbitrage du
19 août a corrigé pour l'entrée trop étroite — « le refus expurgé en
`Unavailable` laissait l'humain deviner » — et qui demeure ici.

### Écart n°4 — suivre le conseil du produit produit le même silence

L'humain qui reçoit le refus « élargir l'entrée à `ALL` » et l'applique de la
façon évidente — un fichier `/etc/sudoers.d/…` avec `NOPASSWD:ALL`, en restant
dans le groupe `sudo` — obtient **deux** entrées au listing. Le produit exige
une entrée unique (`single_entry` → `AmbiguousPolicy`), et rend la **même**
phrase muette. Suivre le conseil du produit casse le produit.

### La forme que le produit exige — et que rien ne documente

Mesurée par élimination : le compte doit être **hors du groupe `sudo`** et
porter **exactement une** entrée `NOPASSWD`. Aucune page, aucun écran, aucun
message ne le dit. Sur cette configuration, tout fonctionne.

## Le parcours, sur la configuration exigée

```text
audit    : La machine a été auditée en lecture seule. Rien n'a été écrit.
install  : Le lot est posé et vérifié sur la machine. Rien n'écoute encore.
activate : Le Controller est actif sur la machine.
```

**30 secondes**, du premier clic à la troisième phrase, depuis la Console
publiée. Relevé indépendant sur le serveur :

```text
ii  your-cloud-server  0.1.3  amd64    (dpkg)
your-cloud-controller.service  active=active   enabled=enabled  Type=notify  NRestarts=0
your-cloud-daemon.service      active=inactive enabled=disabled
your-cloud-relay.service       active=inactive enabled=disabled
```

Le Controller est actif et stable, une seule unité en écoute, sur une machine
où le produit est arrivé **par la page** — jamais par le dépôt.

## Les deux écarts mineurs

- **Écart n°5 — rien ne dit comment lancer la Console.** Le produit, lui, le
  dit : le paquet livre `/usr/share/applications/Your Cloud.desktop` et son
  icône, donc l'application apparaît au menu sous « Your Cloud ». Le README
  devrait le nommer. À noter au passage : `Categories=` y est **vide**, ce qui
  laisse certains menus la classer nulle part.
- **Écart n°6 — rien ne dit comment relever l'empreinte de la clé d'hôte.** Le
  formulaire nomme le format (« `SHA256:…` — confirmée hors bande ») mais pas
  le geste. Une machine ordinaire porte trois clés d'hôte (RSA, ECDSA,
  ED25519) : le produit négocie `ssh-ed25519` en premier (mesuré dans
  `algorithms.rs`), donc c'est cette empreinte-là qu'il faut relever —
  `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.

## Ce que cette passe confirme d'ailleurs

- **`#156`** est vrai sur le trajet public : après une pose réussie,
  `/home/inconnu/.your-cloud-bootstrap` survit sur le serveur.
- **Le temps réel du trajet**, hors écarts : lire la page et télécharger,
  moins de 2 s ; installer, ≈ 3 min 48 s dont l'essentiel en dépendances ;
  le parcours, 30 s.

## Une correction au rapport du palier

La phase `constats` de [`#147`](v0.1.3-controller-install.md) écrivait
`dpkg-query -W -f="${Package} …"` : le shell de la machine cible développait
`${Package}` en **vide** avant que `dpkg-query` le voie — le piège que la
mémoire du LAB nomme pour les commandes fixes du produit, et qui a mordu le
harnais. La ligne d'inventaire du constat n°5 était donc **vide**, sans que
rien ne rougisse. Les deux harnais lisent désormais `dpkg -l <paquet>`, et le
relevé vrai est celui cité plus haut. Le constat n°5 n'est pas invalidé — sa
confrontation reposait aussi sur `dpkg -L` et sur les modes relevés par
`stat`, qui, eux, ont bien été rendus — mais sa ligne de version et d'état
manquait.

## Où en est chaque critère de `#149`

| Critère | État |
|---|---|
| chaque commande jouée est celle du README, dans son ordre, sans commande de secours | **TENU** au rejeu du soir — la phase `installer` **lit** les quatre commandes dans le README publié et les joue dans son ordre : `sha256sum`, `apt update`, `apt install ./…`, `--verify-embedded-server-bundle`. Aucune commande de secours ; la seule main du harnais répond « y » à l'invite que `apt install` assume |
| l'empreinte publiée correspond au fichier téléchargé, et le refus est mesuré si on altère le fichier | **TENU** — concordance exacte, et un octet inversé refusé |
| le rapport LAB nomme le temps réel du parcours et chaque écart rencontré | **TENU** — ce rapport |

## Le rejeu du soir — les trois critères tenus

Après `#157` (les deux refus nomment) et `#150` (le README publie son
installation), la preuve a été rejouée depuis l'instantané `vierge`.

**L'oracle lit le README au lieu de le recopier.** La phase `installer` va
chercher le README de la branche par défaut — celui qu'un inconnu voit en
arrivant sur le dépôt —, extrait les blocs de « Installer (Linux) » qui
s'exécutent sur le poste, et les joue dans son ordre. Un harnais qui porterait
sa propre copie des commandes mesurerait sa fidélité à lui-même. La phase
`serveur` fait de même avec le bloc « Préparer la machine », joué sur la
cible : la politique sudoers n'est plus inventée par le harnais, elle est
celle que le produit documente.

```text
--- README, commande 1 : sha256sum your-cloud_0.1.3_amd64.deb       code=0
--- README, commande 2 : sudo apt update                            code=0
--- README, commande 3 : sudo apt install ./your-cloud_0.1.3_amd64.deb  code=0
--- README, commande 4 : --verify-embedded-server-bundle            code=0
    VERIFIED version=0.1.3 target=debian-13-amd64 size=6082424 sha256=a9658b62…
ECARTS_README=0
```

Puis le parcours : les trois phrases, **31 secondes**, et le relevé
indépendant sur le serveur — `your-cloud-controller` `active` sous
`Type=notify`, `NRestarts=0`, une seule unité en écoute.

**Deux défauts du harnais, trouvés par la mesure et corrigés :**

- la boucle qui jouait les commandes lisait la liste sur l'**entrée standard**,
  si bien qu'`apt install` — qui demande de confirmer ce qu'il va poser — a lu
  la commande suivante pour réponse et s'est interrompu. La liste se lit
  désormais sur le descripteur 3, et l'entrée standard reste à la main de
  l'humain, qui répond « y ». Ce n'est pas une commande de secours : c'est la
  réponse à une invite que le README assume ;
- une passe qui trouvait l'état d'une passe précédente rendait un déroulé
  « incertain — établi par personne » : ce n'était pas un défaut du produit
  mais un harnais qui n'avait pas rangé. `parcours` refuse maintenant de
  commencer sur une cible qui porte encore quelque chose.

**Une mesure de durée à ne pas croire.** L'horloge de la machine nue est
corrigée par NTP pendant la passe (`apt` le signale : « Not live until … »),
et la durée relevée pour `apt install` en devient absurde. Le chiffre honnête
reste celui de la première passe, sur une machine dont l'horloge n'a pas
sauté : **environ trois minutes**, dont l'essentiel en dépendances.

**Ce que le rejeu ne change pas.** La page sert toujours le paquet `v0.1.3`,
donc les phrases nommées de `#157` n'y sont pas : le README le dit
explicitement plutôt que de promettre le prochain paquet. La forme de compte
exigée reste celle que `#158` porte comme dette de contrat.

## La publication de la `v0.1.4`, mesurée par cette preuve

La `v0.1.4` a été publiée le 20 août 2026 avec, pour **critère de
publication**, le rejeu de la phase `installer` depuis l'instantané `vierge` —
c'est-à-dire le README relu chez lui et joué sur le paquet réellement
téléchargé depuis la page.

```text
publiée : cc04a829a6e4463d57d331706a52d9080bfceff4b00cfd9be7cbc3f8be24ae91
mesurée : cc04a829a6e4463d57d331706a52d9080bfceff4b00cfd9be7cbc3f8be24ae91   CONCORDE
altéré  : b17a85e0ee325b1b04101c99705e7257aeabea90f419763b519f0ffeb5f4ae12   REFUSÉ
ECARTS_README=0
VERIFIED version=0.1.4 target=debian-13-amd64 size=6081656 sha256=8ad82553…
```

Le lot serveur embarqué est reproductible une troisième fois : reconstruit sur
`lab-console` depuis la révision taggée, `origin=rebuilt`, **mêmes octets** que
celui né dans le conteneur épinglé et signé hors ligne.

**Ce que la version annonce en titre, mesuré sur le paquet publié.** Les notes
disent que les refus nomment leur cause ; les deux ont été joués depuis la
page, sur les deux configurations que la `v0.1.3` rendait muettes :

- *compte du groupe `sudo` avec un fichier `NOPASSWD` en plus* — l'écran rend
  « Le compte prêté porte plusieurs entrées sudoers, et rien ne dit laquelle
  s'applique : l'Assistant refuse de deviner. Le geste exact : retirer le
  compte du groupe qui lui donne sa seconde entrée […] », **suivi des entrées
  vues** : `Sudoers entry: /etc/sudoers ; Sudoers entry: /etc/sudoers.d/90-inconnu` ;
- *compte administrateur Debian ordinaire* — l'écran rend « L'entrée sudoers du
  compte prêté ne peut pas être lue sans son mot de passe — et c'est cette
  lecture qui permet de vérifier qu'y envoyer un mot de passe est sûr […] »,
  avec les deux postures qui fonctionnent et le renvoi à la dette ouverte.

Là où la première passe mesurait « Rien n'a été approuvé » — la phrase de qui
n'a rien décidé — l'humain lit désormais la cause et le geste. La dette de
fond, elle, reste entière : servir la posture à mot de passe appartient à
`#158`.

## Reproduire

```bash
tests/lab/v0.1.3/from-releases/prove all
```

La phase `installer` est **l'oracle du premier critère** : elle est rouge tant
qu'un écart demeure, et elle deviendra verte quand le README publiera les
bonnes commandes. Le poste se rend à son état nu par
`tools/labctl revert lab-vps vierge`.

Artefacts : `tests/artifacts/proofs/from-releases/20260820T164138Z-211868/`
(locaux à la machine de preuve, `proofs/` n'est pas suivi par git).

## Ce que cette passe ne prouve pas

- **Qu'un humain ait lu quoi que ce soit** : les instruments attestent ce que
  les surfaces rendent, jamais une lecture.
- **Le téléchargement par navigateur** : le harnais emploie `curl` sur l'URL
  que la page publie ; un navigateur graphique n'est pas piloté ici.
- **Une machine sans réseau vers `github.com`** : le poste du LAB a une sortie
  Internet, et c'est la condition même du parcours mesuré.
