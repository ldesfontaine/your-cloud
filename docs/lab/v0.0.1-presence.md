## Contrat matérialisé

| Donnée ou autorité | Origine | Destination | Limite prouvée |
|---|---|---|---|
| identifiant synthétique | configuration root-owned du Daemon | liste positive Relay | exactement `lab-coordinateur` ou `lab-machine-1` |
| version `v0.0.1` | exécutable commun | contrôle de compatibilité | une valeur exacte |
| heure déclarée | horloge de la VM | information Relay | RFC 3339, jamais source de fraîcheur |
| heure de réception | horloge Relay | calcul d'état | `recent` avant 4 s, `old` à partir de 4 s |
| candidature Relay | manifeste local root-owned | garde avant écoute | schéma exact, aucun secret, aucune élection |

L'horloge de `lab-machine-1` était décalée de quatre jours par rapport au Relay.
La machine est néanmoins restée `recent` tant que ses signaux arrivaient : le
Relay a donc réellement utilisé son heure de réception.

refuse les doublons et machines supplémentaires, lie le listener au PID Relay
et éprouve les bornes réseau contre un serveur muet strictement local au LAB.

Chaque cycle écrit un `result.json` expurgé et borné : révision, empreintes,
topologie, cibles, fenêtre horaire Relay, vingt étapes et statut du nettoyage.
Les logs bruts, secrets et valeurs extérieures à cette liste n'y entrent pas.
Ce fichier et les codes de sortie des assertions restent l'autorité.

P2 transforme ce résultat en tableaux Markdown et page HTML dans `lab-console`,
puis sert la page uniquement sur `127.0.0.1:18080` sous `nobody` (UID 65534).
Le pilote vérifie le contenu et le listener, injecte d'abord un échec de capture,
affirme l'arrêt du serveur, puis produit avec Chromium headless un PNG de taille
bornée. Les vingt identifiants d'étape sont affirmés dans Markdown et HTML. Le
contrôleur P2 vient du même snapshot haché que le lot exécuté. Les archives
horodatées vivent désormais sous
[`artifacts/proofs/v0.0.1/`](../../artifacts/README.md) et restent des artefacts
locaux non versionnés. `dist/` désigne uniquement le binaire transitoire produit
dans le runner.

a refusé libvirt avant toute mutation, puis la première assertion

corrigée observe l'événement de limite, le refus avant `reset-failed` et la

Le run `20260717T091821Z-1389363` a ensuite échoué pendant le scénario

Sur le VPS, les unités sont simultanément `active/running`, avec

## Défaut sûr du rôle Relay

Sur `lab-machine-1`, le fichier commun était installé mais aucun manifeste
candidat n'existait. Une invocation directe a quitté avec le code `2` avant
toute écoute :

```text
your-cloud: relay candidate: candidate file: lstat
/etc/your-cloud/relay-candidate.json: no such file or directory
```

La liste des ports avant et après ne contenait pas `8443`. Le script
`enable-relay` a aussi refusé cette machine avant effet :

```text
this v0.0.1 machine is not the Relay candidate
```

Une identité pourtant autorisée mais posée sur le mauvais hôte a aussi été
refusée avant effet, et le binaire audité a refusé une écoute sur `8444` avant
de consulter la candidature. Aucun listener supplémentaire n'est apparu.

Sur le VPS, rendre temporairement le manifeste modifiable par groupe et autres
(`0666`) a fait échouer le Relay avec la cause exacte suivante, sans arrêter le
Daemon et sans ouvrir le port :

```text
candidate file: must not be writable by group or others
Relay  MainPID=0 · ActiveState=failed
Daemon MainPID=2808 · ActiveState=active
```

Les redémarrages bornés de systemd ont atteint leur limite après cinq refus. Ce
test a révélé que la réparation devait aussi effacer cet état d'échec ;
`enable-relay` exécute désormais `reset-failed` avant de relancer l'unité. Le
manifeste valide a ensuite rendu le Relay actif et les deux machines `recent`.

Les tests Go exécutés dans le LAB refusent aussi un manifeste vide,
surdimensionné, mal formé, suivi d'un second objet, avec champ inconnu ou
dupliqué, mauvais schéma ou rôle, fichier non-root, lien symbolique et
répertoire modifiable.

Le retrait échoue fermé lui aussi. Un Relay synthétique lancé hors de l'unité
officielle a fait quitter `disable-relay` avec le code `1` ; le manifeste est
resté présent. Un Daemon synthétique hors unité a ensuite fait quitter
`remove-agent` avec le code `1` ; le binaire commun est resté présent. Les
fichiers n'ont été supprimés qu'après arrêt explicite de ces deux PID.

## Résultat nominal avec `QUERY`

La lecture utilise `QUERY /v0/machines`, `Content-Type: application/json` et le
corps exact `{}`. Le Relay annonce `Accept-Query: "application/json"` et
`Cache-Control: no-store`. Les deux routes refusent toute partie d'URI après
`?`, même vide. Le signal reste `POST /v0/presence`, car il remplace le dernier
état reçu et n'a donc pas la sémantique sûre et répétable de `QUERY`.

```json
{
  "stale_after": "4s",
  "machines": [
    {"machine_id": "lab-coordinateur", "status": "recent", "daemon_version": "v0.0.1"},
    {"machine_id": "lab-machine-1", "status": "recent", "daemon_version": "v0.0.1"}
  ]
}
```

## Refus HTTP et indépendance réellement exécutés

| Entrée | Attendu | Obtenu | Relay après le refus |
|---|---:|---:|---|
| `machine_id` absent | 400 | 400 | actif |
| identifiant `../root` | 400 | 400 | actif |
| ancienne machine `lab-machine-2` | 400 | 400 | actif |
| `machine_id` dupliqué | 400 | 400 | actif |
| clé `Machine_ID` avec mauvaise casse | 400 | 400 | actif |
| champ inconnu `command` | 400 | 400 | actif |
| corps de 513 octets | 413 | 413 | actif |

La frontière `QUERY` refuse aussi l'ancien `GET` avec `405`, l'absence de
`Content-Type` avec `400`, un type autre que JSON avec `415`, puis `null`, un
filtre non prévu, un second objet et un corps de plus de 32 octets. La
revalidation vivante a couvert ces cas, les méthodes croisées et les parties
query non vide ou vide. Elle a vérifié après chacun le même PID Relay, le
listener exact et une consultation valide `200` non cacheable.

Le Relay ne journalise aucun succès par signal. Une panne répétée ne produit
qu'une transition `presence unavailable`, puis une transition
`presence recovered` au retour ; le test LAB a confirmé l'absence de log à
chaque seconde.

Après arrêt du seul Daemon VPS et cinq secondes :

```text
lab-coordinateur old
lab-machine-1    recent
Relay PID avant=5990 · après=5990
```

Le redémarrage du Daemon a ramené les deux états à `recent` sans changer le PID
Relay. Avec les deux Daemons arrêtés, redémarrer le Relay a donné exactement
deux états `absent` ; leur redémarrage a ramené deux états `recent`.

## Désactivation, retrait et état final

`disable-relay` a retiré l'unité, la configuration et le manifeste Relay. Le
port `8443` était fermé, tandis que le Daemon VPS restait `active`, le binaire
commun conservait la même empreinte et aucun fichier Daemon n'était retiré.

Le retrait complet a ensuite produit sur `lab-coordinateur`, `lab-machine-1`
et l'ancienne `lab-machine-2` :

```text
Daemon LoadState=not-found · MainPID=0
Relay  LoadState=not-found · MainPID=0
/usr/local/lib/your-cloud absent
/etc/your-cloud absent
```

Le même lot a enfin été réinstallé. État laissé dans le LAB :

- `lab-coordinateur` : Daemon et Relay actifs depuis le même exécutable ;
- `lab-machine-1` : Daemon actif, unité Relay absente ;
- `lab-machine-2` : aucun composant Your Cloud ;
- Relay : deux machines `recent`.

## Limites et risque résiduel

- HTTP sur `8443` n'apporte ni TLS ni authentification ; le numéro du port ne
  change pas cette limite.
- Un pair présent dans le LAB et capable d'atteindre le Relay peut lire ou
  usurper un signal autorisé.
- Le manifeste candidat évite une activation accidentelle ; root conserve par
  définition l'autorité de modifier le système et pourrait contourner cette
  garde.
- Le Relay conserve seulement le dernier signal en mémoire ; son redémarrage
  rend les machines `absent` jusqu'au prochain envoi.
- Un défaut du fichier partagé peut toucher plusieurs rôles malgré leurs
  comptes distincts. Le rollback minimal `v0.0.1` est prouvé, mais signature,
  SBOM, provenance et stratégie de déploiement progressif restent nécessaires
  avant la preuve finale V1.
- Aucune interface, métrique système, mTLS, App, Auxiliaire, base, tampon,
  Ansible métier, conteneur, WireGuard, élection ou remplacement automatique de
  Relay n'a été implémenté ou simulé.
- Les contrôles OWASP et NIS2 cités justifient les choix proportionnés ; ils ne
  constituent aucune déclaration de conformité.
